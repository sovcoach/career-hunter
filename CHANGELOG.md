# Changelog

All notable changes to this project are documented here.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this
project uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- Each application keeps its job description (ADR-024). EI migration 0002 adds an append-only `job_descriptions` table (the text verbatim, its SHA-256, `jd_source` and its snapshot file) and `applications.jd_expected`; search migration 0020 adds `applications.jd_expected`, `jd_sha256` and `jd_path`. Applications recorded before them get `jd_expected` 0 and show as pre-feature; every application recorded from now on gets 1. A corrected JD is a new row, and the latest is current.
- `/log <link> | method | date [| Company | Title]` takes the job description on the lines after it. Telegram splits a long paste into several messages, so plain text messages that follow within 4 seconds of each other are joined to it with a blank line between each (Telegram splits at blank lines and drops them), and the application is recorded once they stop. A pasted job description is stored as Telegram delivered it: Telegram turns tabs into spaces and trims trailing spaces, so a file is the way to keep the exact text. A PDF, HTML or text file captioned with the `/log` line is the job description too. Without one (and none on the page), the application is recorded and the reply asks for the job description as a reply. A text that arrives just after the window gets a reply saying to send the whole description as a `.txt` reply to the `Recorded` message. No reply repeats a job description, and the bot log counts only its messages.
- `careerhunter log` takes `--jd-file PATH` (PDF, HTML or text) or `--jd-stdin`, not both. Without either, `/log` and `careerhunter log` fetch the job description from the page's JSON-LD or the ATS's public JSON.
- An encrypted PDF is refused, and nothing is saved. A PDF with no text, such as a scan, is kept as the job-ad copy, and the application stays flagged until the job description is sent as text.
- A job description's file becomes the job-ad snapshot when there is none, so LinkedIn applications get one (ADR-017 as amended).
- `doctor` has a `job descriptions` line: WARN with the count of applications missing one, `--` with the count from before job descriptions were kept.
- `careerhunter report` shows each application's canonical link and its job description by reference: `JD <first 8 of sha256> (<source>)`, `JD missing` or `JD missing (pre-feature)`. The export's CSV and PDF get the same column, and the export writes a `<stem>-job-descriptions/` folder (0700) with one `.txt` per application (a header, then the verbatim text) and a copy of each original file (0600). Both still read a claim file at EI schema 1.
- `reconcile` (and so `doctor`) also compares `jd_expected`, the current job description's hash and the canonical link between the two layers.
- `careerhunter import <file> [--dry-run]` backfills applications and their job descriptions from a version 1 JSON file (see `import.example.json`). The file, and every `jd_file` it names, must sit under `imports/` in the data folder, which `init` now creates (0700) and `doctor` keeps owner-only. Each entry is matched on the employer (folded, without a leading "The" or legal suffixes) and the title (folded, with `Analyst, Client Experience` read as `Client Experience Analyst`) and listed as CREATE, ATTACH, UNCHANGED, AMBIGUOUS (with its candidates), CONFLICT or REFUSED, with the job description shown only as its hash and length. `"resolve": <app id>` or `"new"` settles an ambiguous entry, `--route-out-of-claim-to-search` sends out-of-claim entries to `search.db` only, nothing is fetched, an application's date never changes, and notes stay in `search.db`. `--dry-run` writes nothing; a run applies exactly its lines, and a second run reports every entry unchanged. Exit 0 when all are done or unchanged, 1 when any is left (after applying the rest), 2 when the file is outside `imports/` or an earlier claim is unsealed.
- Lane matching tries a normalized rule when no lane title matches literally: a lane title of two or more words then `Specialist`, `Analyst` or `Associate` matches a posting with the same words and any of the three, ignoring level words (Junior, Senior, I to IV, 1 to 4, Level N) and after comma inversion, with the role word at the end of the title or before a comma, dash or bracket. `IT Support Specialist` matches `Senior IT Support Associate II` and `IT Support Associate - Night Shift`, not `IT Support Associate Manager` or `IT Support Lead`. A one-word core only matches literally. Comma inversion also sets aside level words in the head, so `Senior Analyst, Client Experience` is equivalent to `Client Experience Analyst`.
- `careerhunter lanes reassign [--dry-run]` recomputes every checked posting's lane against the current config and matcher. `--dry-run` lists each move and the counts, including how many held off-lane postings would become alertable, and writes nothing. A run applies the same moves in one transaction. Released postings alert as usual, within `alerts.max_per_poll`, and one past the posting-age gate gets a `too_old` skip. It refuses without `search.lanes`.

### Changed
- A logged link is saved in its canonical form: lowercase scheme and host, no fragment, no tracking parameters (`utm_*`, `trk`, `refId`, `trackingId`, `gclid`, `fbclid`, `gh_src` and the like), and LinkedIn job links as `https://www.linkedin.com/jobs/view/<id>/`. Links already stored are left as they are and compared canonically. The watcher's links are unchanged.
- LinkedIn is never fetched: `fetch.py` refuses `linkedin.com`, its subdomains and `lnkd.in` for every caller, on the first link and every redirect hop. A LinkedIn `/log` or `careerhunter log` needs the company and title, and the refusal says how to give them. SETUP suggests logging the company career-site link the posting leads to instead.
- A `/log` with no job description, and every Applied from an alert, asks for the job description instead of a PDF or screenshot of the ad: the watcher keeps no description to attach. A reply with a file also becomes the ad copy when none was saved. A request for the ad sent before this version still takes a PDF or image.
- The PDF reader moved from `resume.py` to `pdftext.py`, shared with job descriptions. Resume import behaves as before.
- `doctor`'s `bot service` and `watch service` lines name the checkout and data folder each agent serves, from `launchctl print` for a loaded agent and from its plist otherwise. launchd labels are per user, so against another data folder (a test volume) they describe the live agents: the line then says `not this CAREERHUNTER_DATA_DIR`, and an OK becomes a WARN. A label launchd has disabled is BAD on its line, with the exact `launchctl enable` command, even when the agent isn't installed.
- `search.db` moves to schema version 20 and the EI record to version 2. Back up and run `careerhunter migrate`. A sealed claim's file is not migrated, and is still read.
- Search migration 0021 (schema version 21) lets a checked lane move, only through `lanes reassign`: it drops the set-once trigger, keeps `lane_checked` at 1 once set, and logs each move of a checked lane to a new `lane_changes` table. EI files are not changed. After `migrate`, run `careerhunter lanes reassign --dry-run`.

### Fixed
- A launchd label left disabled made `careerhunter service install` fail with launchctl's error 5 and its suggestion to run as root. `service install` now checks every label it would install before writing a plist, and stops with the exact command: `<label> is disabled in launchd. Run: launchctl enable gui/<uid>/<label>, then careerhunter service install`. It never enables a label itself, and `uninstall` still leaves the override alone. A failed bootstrap gets a fixed message, `launchctl bootstrap failed (<code>)`, without launchctl's text; code 5 adds a pointer to `launchctl print-disabled`. Nothing suggests root or sudo.
- After retiring the old separate discovery agent, `service install` no longer reports success when installing the bot or watch agent failed for any reason other than both being installed already.

## [0.4.0] - 2026-11-10

### Added
- The project is MIT licensed (ADR-021). See `LICENSE`.
- `docs/SETUP.md` covers what 0.4.0 needs: LM Studio is required, with a guide to choosing chat and embedding models for the Mac's memory; the services are installed from a separate release checkout (`git worktree add ../career-hunter-release v0.4.0`, then `uv sync --locked`), never from a development one; and "Upgrading to a new release" gives the order: stop the services, back up the whole data folder (SQLite `.backup` for every database file, a copy keeping permissions for the rest, then an owner-only check), move the release checkout, add a fit to every gap tier, `doctor`, `migrate`, `resume import` then `search.resume: resume/current.txt`, `doctor`, and install the services again. Its expected outputs are taken from runs of this version on synthetic data (#44).
- `careerhunter demo` runs the watch pipeline on synthetic data: an in-memory `search.db` and EI record, a synthetic config, two fake boards and a fake local model. It prints the watch lines, the digest the bot would send (not sent) and the EI row of one application recorded through the ledger. It never reads `CAREERHUNTER_DATA_DIR`, does not run the storage guard because no data folder is used, writes no file and opens no socket; ADR-009 is unchanged (#44).
- `scoring.chat_model` and `scoring.embedding_model` name the models the scorer and the embedder ask for on LM Studio. Both are optional: unset or null sends `local-model` and `local-embedding`, as before. Each is text of 1 to 200 characters with no control characters and no leading or trailing spaces, and any other key under `scoring` is refused, so the loopback URLs stay constants. Stored vectors do not record the model; after a change they are compared as they are (#44, ADR-019, ADR-023).
- `/log <link> | method | date` in Telegram, and `careerhunter log <link> --method … --date …` on the Mac, record a job you found and applied to yourself in one step: the posting (`source` self_sourced) and the application go to both layers under one correlation ID, through one ledger call, with a job-ad copy when the page gives one. A bare `/log <link>` asks for the method and the date with buttons, and writes nothing until the last step. `| Company | Title` after the date, or `--company` and `--title`, fill in what the page doesn't show; this replaces the `/log <link> | Company | Title` form of 0.3.0. The reply is `Recorded: <company> — <title> (ref aN).` The date is checked against the claim before anything is fetched or written, and without a readable `config.yaml` nothing is fetched or recorded (#34, ADR-015).
- When a logged role was logged before (the same company row and title key), the application is still recorded, and the reply adds one line with the earlier date only: `You logged an application to this role on 2026-10-27.` The CLI and `/log` both do this (#34).
- `careerhunter report --claim <label>` joins one claim's EI record to `search.db`, both opened read-only, into a private report under `reports/` (0600) and prints only its relative path: each application's EI facts beside its lane, fit and source, with counts by lane. It is the only code path that attaches a database; a test fails if `ATTACH` appears anywhere else (#34, ADR-014).
- The watcher never alerts a posting the operator logged or skipped, or a repost of it: the same company row and `filters.title_key`, which drops a bracketed or trailing requisition code (one token with at least three digits, such as `(R12345)` or `- 104332`) and keeps segments such as `(Level 2)` and a trailing year such as `- 2026`. A repost is skipped as `already_handled` when stored, and every run skips any unalerted posting that became one. Search migration 0016 adds `skips.by_operator`; only skips the operator chose suppress reposts, and skips stored before it are not filled in (#34, ADR-005).
- `doctor` names an application on one side only, in either direction, as an `orphan`, says it fixes neither file, and leaves both unchanged (#34).
- `doctor` checks `reports/` like the other private folders (#34).
- Separate "ran" and "did useful work" records for watch and discovery: `watch_runs.useful` and `discovery_state.useful_at` and `unproductive` (search migration 0018). `doctor` shows the last useful run and pass, and warns after `health.unproductive_runs` (default 3, 1 to 50) in a row that did no useful work (#42, ADR-022).
- After `health.failure_runs` (default 3, 1 to 50) watch runs in a row that failed the local model, SearXNG or every board, the bot sends one message naming the component, the count and the postings held for scoring, and one more when it works again. No host or path. `component_health` (search migration 0018) records what was sent, so each outage gets one of each; `doctor` shows a failing component too (#42, ADR-015).
- Telegram refusals of an alert are counted per posting in `alert_refusals` (search migration 0017), so a restart remembers them. After three, the bot gives the posting up: it is never sent again, stays unalerted, and `doctor` warns with the count (#42, ADR-015).
- `logs/watch.log` and `logs/discover.log` are rotated with the standard library's `RotatingFileHandler`: at 5 MB, when a run opens one, keeping five older files in `logs/`, every one at 0600 (#42, ADR-022).
- The scoring prompt shows the local model up to `learning.labelled_examples` (default 5, 0 to 20) of the operator's most recently labelled postings: title, lane, gap count and label (an application's latest status, or `skipped`). Labels come only from the operator. The examples reach the loopback request only; rules and thresholds never change by themselves, and embeddings stay out of the decision (#43, ADR-023).
- `alerts.weekly_digest: {day, hour}` sends a weekly message of counts by lane (alerts, Applied, Skipped, responses, outcomes) at that local time in `schedule.timezone`, once a week, with no titles, notes or gap names (#43, ADR-015).
- A sentinel test plants a value in every `search.db` field added since v0.3.0, runs every path that writes an EI file, and proves none reaches it. An AST test fails if any module the watcher reaches imports `ei_store` (#34).
- SmartRecruiters, BambooHR and Workday boards are watched. SmartRecruiters is read from its public Posting API, BambooHR from a company's public careers list, and Workday from its careers site's job list, a JSON POST. Every board-API GET asks for `application/json`; the JSON parse stays the gate, so an HTML 200 stores nothing and fails the board. Workday paging stops at a page whose `externalPath`s repeat the page before, keeping what was read, with a `repeated page` note, the same as the page limit. Their lists have no descriptions, so each posting not stored yet gets one detail request, at most 40 per board per run; the rest wait for the next run. A detail that answers another status or a bad body leaves out that posting only; a fetch error or HTTP 429 stops the board's details, keeps what was read and fails the board. All of a board's replies count against the 20 MB cap together. Every gate runs on every ATS (#35).
- A Workday board is watched per employer: `ats_slug` is the tenant, with `ats_host` (the wdN host) and `ats_site` on the watchlist entry. Search migration 0012 stores both on the company and rebuilds `discovery_candidates` for the new ATS types, Workday's identity and the status `gone`; nothing references that table, so the rebuild needs no foreign-key pragma (#35).
- `fetch.post_json` sends one JSON POST with the same address pinning, caps and deadline as a GET; a redirect is not followed. A board's POST goes only to a subdomain of `myworkdayjobs.com` over https: `ats.Client.post_json` refuses any other host before it is looked up (#35).
- `search.max_posting_age_days` (default 7, 1 to 365) skips postings older than that as `too_old`, by the posted date each ATS gives (see ARCHITECTURE.md), or by the day first seen, with a line, when it gives none. Search migration 0013 stores `postings.posted_date`, and the recheck applies the same gate to postings still waiting unscored (#36).
- Discovery walks every combination of titles (lanes by priority, every variant), places (`search.location_rules`) and hosts (Greenhouse, Lever, Ashby, SmartRecruiters, BambooHR, `myworkdayjobs.com` and `discovery.career_hosts`) with a cursor in `search.db` (search migration 0014), taking the next `discovery.queries_per_run` (default 12, 1 to 40) each pass and wrapping around (#40).
- Discovery queries are `discovery.query_delay_seconds` apart (default 5, 2 to 30). HTTP 429, or an engine SearXNG reports for a CAPTCHA or too many requests, stops the pass. A failed pass backs off exponentially from `discovery.interval_minutes`, at most seven days (#40).
- A discovery hit that is a posting URL on a supported ATS is fetched once through that ATS's API and goes through the same gates, age gate, scoring and digest as a watched posting. No approval is needed first (#41).
- A discovered board is queued only after one board-API request confirms it. A board that does not exist is stored as `gone` and never queued again, and a company in `exclusions.companies` is never queued, matched on its slug and on every company name the confirming reply gives (#41).
- Each row of a discovery digest has its own Approve and Reject tokens, so one tap leaves the others valid (#41).
- Search migration 0015 stores each posting's identity on its board (`postings.ats_key`: ATS, board and posting id). A Workday posting's id is the trailing `_<id>` of its `externalPath`, as it is (`JREQ205219-7` keeps its suffix), so a retitled or moved posting is the same posting; search migration 0019 clears Workday keys stored in the older whole-path form, to be set again when the watcher next meets the posting. The watcher matches a stored posting on its key before its URL, and a posting whose key is stored gets no detail request. Discovery checks it, with the URL, before fetching a posting, so a Greenhouse posting on the company's own domain is not fetched again. Stored postings and already-queued, gone or excluded boards are left out before the per-pass limits count, and each pass starts at a different place, so every pass reaches new postings and boards (#41).
- The bot sends watcher postings as one digest per watch run. Each row shows the company, title, location, lane, fit, the number of gaps, the schedule flag, up to three key requirements and the link, with its own Applied and Skipped buttons; tapping one row leaves the others' buttons working. At most `alerts.max_per_poll` (default 10, validated 1-50) go per poll and the rest carry over; older runs go first, and a run's postings wait until it finishes. Every message stays within Telegram's length limit. Gap names are never sent (#39, ADR-015).
- Scoring asks the local model for up to three key requirements stated in the posting. A phrase is capped at 60 characters and dropped if it contains a gap name or copies 40 characters of the resume. Search migration 0011 stores them in `postings.key_requirements`, with the scoring run in `postings.score_run_id` (#39, ADR-022).
- Telegram client errors say whether Telegram could not be reached, rate-limited the call, refused it, or sent a reply that isn't the Bot API's JSON. A refused digest is sent again one row per message (#39).
- Greenhouse boards are fetched with their descriptions (`content=true`), turned from HTML into text with the standard library. Lever adds its lists, closing text and salary description, and Ashby its salary summary (`includeCompensation=true`). Every gate runs on every supported ATS. The text is used in memory only (#32).
- A board fetch has a 20 MB cap. A board over it logs `board over the size cap (...); nothing recorded`, stores nothing from that board and counts as failed (#32, ADR-022).
- With `search.location_rules` set, a posting with no location text and no work model from the board is skipped as `empty_location`. A board work model stands in for the location (#32).
- Every `fit_rubric.gap_tiers` tier needs `fit: low`, `medium` or `high`, and validation names every tier without a valid one in one problem. A boundary outcome takes the fit of the tier it names. A score stores that fit in `postings.fit` (search migration 0009), in the same UPDATE as the score and the resume hash. Every watch run fills in the fit of scored, unalerted postings stored without one, by their tier name. A name no longer in config stays without a fit (#38, ADR-023).
- Every alert carries `Fit: High`, `Fit: Medium` or `Fit: Low`. A posting with no fit is held and not alerted: unscored, or scored into a tier name not in config. Once it gets a fit, it is alerted once (#38, ADR-015).
- `watch_runs` (search migration 0009) records each watch run: its start, its finish, the board counts, whether the budget left work, and the postings still held (unscored, no fit, off-lane below the threshold). A run that crashes, is killed or stops on a database error keeps its row unfinished, with no counts (#38, ADR-022).
- `search.lanes` is a filter as well as prompt context. A title is matched against every variant in every lane, as whole words, ignoring case, and the best (lowest) priority wins. The lane is stored once, at insert, skipped postings included, in `postings.lane` and `postings.lane_checked` (search migration 0010, with a set-once trigger). Each watch run checks any posting not yet checked, so postings stored before lanes existed get theirs. Lanes are separate from `never_gated_families` (#33).
- `search.off_lane_min_fit` (low, medium or high, default high): a title that matches no lane is still gated and scored, and alerts only at that fit or better, labelled `Off-lane` (#33).
- Alerts show `Lane: <name>` or `Off-lane` and are sent off-lane last, then by fit, best first, then non-fallback before fallback lanes, then lane priority, then oldest. A stored lane no longer in config sorts as a fallback after every configured lane, before off-lane. Without `search.lanes`, lane checking is off and alerts go by fit, then oldest (#33, ADR-015).
- `doctor` reports whether lane checking is on, a watch run that never finished, the held counts from the last finished run (a WARN for postings with no fit), and alerts the bot is holding because it couldn't read `config.yaml` (#38, #33).
- `careerhunter resume import <file>` reads a PDF or DOCX resume locally, with no network, and writes its text to `resume/current.txt` in the data folder (folder 0700, file 0600). Only its SHA-256 and the time are stored, in `search.db` (search migration 0008, `resume_import`). The format is decided from the bytes. An encrypted PDF, a PDF over 200 pages, any other kind of file, or a file over 10 MB, a `document.xml` over 5 MB, more than 100 zip entries, or more than 50,000 characters is refused, never truncated. A DOCX with a DOCTYPE, a NUL byte, or an encoding other than UTF-8 is refused. Errors are fixed messages with no content and no path, and nothing is stored. The command prints the character count only. One import runs at a time. The file is renamed into place inside the database transaction, and a failed COMMIT puts the previous file back (#37, ADR-023).
- The scoring prompt includes the resume when `search.resume` is `resume/current.txt` and the file matches its import. While it is in use, `llm_output` stores canonical JSON of the parsed gaps, never the model's reply. A reply that copies 40 characters of the resume into a gap name or type, or has one over 120 characters, is treated as one that does not parse, and that posting stays unscored (#37, ADR-023).
- When the resume changes, `careerhunter watch` re-scores stored postings. Each score records the resume hash it was made with (`postings.scored_resume_sha256`). Postings on a fetched board are re-scored with their in-memory description, after all the boards; the rest from stored fields. Never-scored postings go first. Within each pass, `postings.score_attempted_at` puts a posting that keeps failing behind the others. Skipped and applied postings keep their score. An alerted posting is re-scored and not sent again. A failed re-score keeps the old score and hash. What the budget doesn't reach is left for the next run and not counted (#37, ADR-023).
- `doctor` checks the resume: the folder and file modes (tightened if loose), a file that no longer matches its import, `search.resume` set without an import or naming another file, and files left by an interrupted import (#37).
- A test follows a sentinel resume through import, watch and the bot. It is in the scoring request, and in no log, Telegram message, `search.db` or EI cell, exception text or traceback (#37).
- `discovery.searxng_url` and `discovery.career_hosts` are optional and validated (ADR-020). The example leaves the URL null and the host list empty. The URL is plain http to a loopback host, with no userinfo. A career host is a hostname only: no scheme, path, wildcard, or `..`.
- `discovery.interval_minutes` is optional and validated (ADR-020). Missing or null means 1440 minutes. A set value is an integer of at least 60. The example is 1440.
- `careerhunter discover` runs one discovery pass against a local SearXNG by hand, and `discover list` prints the pending rows; the watch agent runs passes itself (see below). Confirmed boards are queued in `search.db` (search migration 0005). The result title and snippet are not stored. A transport failure or a reply over the cap writes `discovery miss: unreachable`; a reply that arrives but can't be used (another status, a body that is not UTF-8 JSON, no `results` list, or no usable url) writes `discovery miss: bad-reply`; either way nothing is stored and the command still exits 0. A null URL makes no request. The EI schema is unchanged (#30, #42, ADR-020).
- `careerhunter discover approve` and `careerhunter discover reject` update that queue in `search.db` only. They do not rewrite config or exclusions and they do not send Telegram. An approved board is fetched on the next `careerhunter watch` when the company source is `discovery` and `watchlist` is 1. A career page row stored by a development build of discovery stays listed, and approving it stores `careers_url` without fetching it. A rejected row inserts no company. The EI file is not written.
- The bot sends each pending discovery row to the allowlisted chat: the suggested name, the reduced URL, and Approve and Reject. Up to five are separate messages. More than five are one message of at most eight, and the rest wait for a later poll. The buttons call the same approve and reject rules and open `search.db` only. Search migration 0006 stores `notified_at` after Telegram accepts the message. A failed send leaves it null. A refusal replies `Not changed.` and leaves the row pending. Nothing is sent while `config.yaml` can't be read. The EI file is not opened.
- `careerhunter watch` reads the watchlist once and records new postings from public Greenhouse, Lever, Ashby, SmartRecruiters, BambooHR and Workday boards into `search.db`. A board that fails, including HTTP 429, is logged and left for the next run; the other boards still run. Other ATS types are not fetched.
- The same run filters each posting. Exclusions, hard gates (language, credential, shift, pay, seniority, and a minimum salary when one is set), location rules, the watchlist entry's role filters and schedule limits run in that order. A decision not to surface a posting is one `skips` row with a reason. A stated weekend-day count above the cap is flagged on `postings.schedule` or skipped, following `over_limit`. An on-call mention is flagged and kept. The word "weekends" on its own does neither. `min_salary: null` leaves that gate off. The watch command does not send alerts, or write applications or EI records.
- Survivors are scored on a local OpenAI-compatible server at `http://127.0.0.1:1234/v1/chat/completions` and nowhere else. The client is not `fetch.py`: loopback only, no redirects. The prompt is lanes, location rules, hard gates and `gap_tiers`. Parsed gaps and the tier name are stored. `fit_rating` stays null. A count at or above `exclude_from_gaps` is a `gap_tier` skip. A model that does not answer (a refused URL, no connection, a timeout, or any status other than 200) stops scoring for the rest of the run, and that posting keeps its place; a reply that does not parse leaves only that posting unscored. The client has a 120-second total, and a broken reply (`IncompleteRead`, `RemoteDisconnected`, `BadStatusLine`) counts as no answer instead of ending the run. The next run scores those rows after it has fetched the boards (#30, #37).
- The bot alerts each watcher or discovery posting that has a score, a fit and no skip, in the digest above. A watchlist company flagged as an agency, with no separate employer stored, is shown as `Name (agency)`. Search migration 0003 adds `postings.alerted_at`, set after Telegram accepts the message. A failed send stays unset and is tried on the next poll. Quiet hours are not implemented.
- `careerhunter scout-prompt` prints one prompt to stdout from the validated exclusions and the hard gates `careerhunter watch` skips on. Empty lists are omitted. It writes nothing: no file, no database, and no model call. Run it again after changing either file. The prompt is not stored in this repo.
- The watcher reads lanes, location rules, gap tiers, hard gates, schedule limits, watchlist role filters, the agency flag, and exclusions. It does not read free-form notes. `search.target_titles`, `search.locations`, `search.work_models`, rubric weights, `max_commute_km`, and `exclude_work_models` stay validated and unused. One `role_filters` block is AND only and cannot express "this work model, or else that place."
- `search.resume` and `fit_rubric.embedding_weight` are optional and validated (ADR-019, ADR-023). The example leaves both null. `search.resume` must be `resume/current.txt`, the file `resume import` writes, and scoring and embeddings read it only through `resume.load`; any other value is refused and `doctor` reports it. `embedding_weight` is a number from 0 to 1. The watcher does not read the weight for skips, alerts, or stored scores.
- `careerhunter embed-eval` ranks stored cosines against stored LLM tiers and writes `evals/embed-eval-<utc>.txt` in the data folder, mode 0600. It does not call the model. The terminal prints the relative path only. Spearman uses midranks and Pearson correlation on those ranks. Precision at 5 and at 10 counts an application as a hit. Fewer than two comparable rows, or a rank with no spread, writes `undefined` and the command still exits 0. When `fit_rubric.embedding_weight` is set, the report also ranks `weight * cosine + (1 - weight) * tier`. That blend is not stored and not alerted.
- The same scoring pass stores a local embedding cosine beside the LLM tier (search migration 0004). Vectors are float32 BLOBs in `search.db`. The client posts to `http://127.0.0.1:1234/v1/embeddings` and nowhere else: loopback only, no redirects, not `fetch.py`, a 60-second total and its own 1 MB reply cap. A missing resume file, a down server (`unreachable`), a reply that is not a usable vector (`bad-reply`), or a dimension mismatch leaves that posting's cosine null, logs `embedding miss posting <id>: <reason>`, and the run still exits 0; after a transport failure nothing more is sent to the embedding server that run. A cosine does not cause a skip and is not sent to Telegram. `fit_rating` stays null. The EI schema is unchanged (#30, #42).
- `careerhunter service install` also installs `org.careerhunter.watch`. It runs `careerhunter watch` once per `schedule.watcher_interval_minutes` (default 60, minimum 15) and exits. A finished run writes `logs/watch.success`. `doctor` reports whether that agent is loaded and how old the stamp is. A stamp older than two intervals is a failure. A changed interval takes effect after `service uninstall` and `service install`. `service uninstall` removes each installed agent.
- Discovery runs inside the watch agent, at most once per `discovery.interval_minutes`, with up to 150 seconds of the run; there is no separate discovery agent. A pass that ran writes `logs/discover.success`, a miss included. `service install` removes an `org.careerhunter.discover` agent left by a development build, `service status` says where discovery runs, and `doctor` reports discovery off for a null URL, warns about a leftover plist, and checks the stamp against two discovery or watch intervals, whichever is longer (#40, ADR-020).
- `AGENTS.md`: the working rules for every AI agent session, the single source of truth; `CLAUDE.md` only points to it. They cover approval before every commit, push or PR, guarded git commands run on their own, no attribution lines, synthetic test data, and placeholder paths with no personal details in public files (#44).
- `make check-lock-age` (`scripts/check_lock_age.py`) checks that every version in `uv.lock` was at least 14 days old when it was first locked. A younger version passes only when `scripts/lock_age_allowlist.toml` lists it, with its exact version and advisory IDs, as a security fix; a listed version no longer in `uv.lock` fails the check (ADR-006, #29).
- `make check-history` (`scripts/check_history.py`) checks that a range of commits, messages included, adds or removes no `/Volumes/` or `/Users/` path other than the placeholders in `scripts/history_path_allowlist.txt`. A finding names the commit and masks the path (#29).
- A **Supply chain** CI job fetches full history and runs the lock-age check on every run and the history check on every pull request (#29).
- A test keeps the ruff and mypy pre-commit hook revisions equal to their locked versions (#29).
- `hard_gates.min_salary` counts only figures in a pay context. Bonus, signing, relocation and equity amounts and figures in another currency than CAD are ignored. Hourly, daily, weekly and monthly figures are converted to yearly (2080 hours, 260 days, 52 weeks, 12 months). A posting is skipped only when the top of its highest range is below the minimum (#32).
- With no work model from the board, a location containing "remote" is treated as remote and any other as on-site for the location rules. An inferred remote posting may match either list. `role_filters.work_models` uses only a positive inference; an unknown work model still passes (#32).
- Never-scored postings are scored first come, first served: by `coalesce(score_attempted_at, created_at)`, then id. A posting that keeps failing to parse is not pushed back by new arrivals. The re-score passes keep their order (#38, ADR-023).
- While the bot can't read `config.yaml` during a poll, it sends no watcher alert, records the hold for `doctor`, and logs only when the hold starts and ends (#33, ADR-015).
- Inline scoring of new postings during a watch run stops once less than 240 seconds of the budget are left. Later new postings are scored after the boards, with their description kept in memory (#37, ADR-022, ADR-023).
- A watch run has a 600-second budget, shared by the fetcher, the scoring and embedding clients and the run itself. The boards come first; the embedding refresh, the recheck and the scoring of waiting rows use what is left, and scoring waits for a complete recheck. Anything the budget does not reach is logged as left for the next run and is not counted. A posting is sent to the scorer at most once per run (#30, ADR-022).
- Boards rotate: search migration 0007 adds `watch_board_attempts`, and boards never tried come first, then the one tried longest ago. A board the budget leaves out keeps its place. `search.db` moves to schema version 7; the EI schema is unchanged. Run `careerhunter migrate` with the services stopped (#30).
- The last line of a watch run is `watch: <n> boards fetched, <m> failed, <k> left`. A board refused for an ATS identity mismatch counts as failed (#30).
- `careerhunter discover` writes its search runs to `logs/discover.log` (mode 0600): the notice, then `discover: <n> queued`. List, approve and reject write no log (#30, ADR-020).
- Discovery queries to SearXNG have a 30-second total each; a `localhost` URL is looked up within it, and only a loopback answer is used. A broken reply, a body that is not UTF-8, no `results` list, or no usable url is a miss (#30).
- Only infrastructure stops a watch or discover run: a missing or invalid `config.yaml`, a missing `search.db`, a database that cannot be opened, migrated or written, or a run log that cannot be written. Each writes an abort line to the log and exits 1 without the success stamp. A database failure prints `error: <Type>: <message>` (#30, ADR-022).
- Seniority words match whole words of the title only, ignoring case, so a junior title whose description mentions senior colleagues is kept; `hard_gates.seniority_in_description: true` checks the description too. `title_exceptions` and `never_gated_families` match whole words as well, so "Art" does not cover "Partner". The scout and scoring prompts state the rule (#31).
- One company's exception does not end a watch run: it is rolled back and logged as `watch: <company>: <ExceptionType>; continuing`, and the other companies still run (#30).
- Each watch and discover line reaches its log file as it happens, because launchd discards stderr, and a crash leaves its traceback there and nowhere else (#30).

### Changed
- `search.db` moves from schema version 2 (0.3.0) to 19, through search migrations 0003 to 0019; the EI schema stays at version 1. Stop the services, back up the data folder and run `careerhunter migrate` before installing the services again: see "Upgrading to a new release" in `docs/SETUP.md` (#44).
- The roadmap in ARCHITECTURE.md lists only what is on `main`, and the README's status, command table and tech list match it: pypdf and truststore are named, and scoring runs on LM Studio (#44).
- The template watchlist is empty: `careerhunter init` copies `watchlist: []`, so `careerhunter watch` makes no network call until the operator adds boards to their own `config.yaml`. The Greenhouse, Lever, Workday and agency examples stay in the template as a commented block (#44).
- `doctor` measures every age against one injected clock, and its tests use a fixed one (#42).
- `db.migrate` applies all pending migrations in one `BEGIN IMMEDIATE` transaction, statement by statement, and commits once. When nothing is pending it takes no write lock. A process that waited for another one's migration re-reads the applied versions and applies nothing twice. A failure rolls the whole run back. A lock held for over 60 seconds fails with a message saying nothing was applied. `executescript` is no longer used (#51, ADR-004).
- pypdf 6.21.4 is a new dependency, with no extras. It is younger than 14 days, so it is listed in `scripts/lock_age_allowlist.toml` as a security fix for ten advisories and given its own `exclude-newer` cutoff. The mypy pre-commit hook pins the same version and has to move with `uv.lock` (#37, ADR-006).
- Pull requests merge on GitHub with "Create a merge commit" once CI passes; a local merge is optional, and its steps are in `AGENTS.md` ("Merging"). ADR-010, ADR-011 and ADR-012 are amended, and CONTRIBUTING.md matches (#44).
- ADR-006 is amended: the two-week rule covers every version in `uv.lock` and every hook and Action pin, a single non-security violator is evicted with a per-package cutoff, and a younger version is allowed only as a listed security fix (#29).
- The lockfile is re-locked under `[tool.uv] exclude-newer = "2026-10-17T17:31:54Z"`, with a per-package cutoff that evicts ast-serialize 0.13.1. Thirteen packages move, including reportlab 5.1.0 to 5.0.1, filelock to 4.2.1 and virtualenv to 21.14.10. pillow 13.0.0 stays as a listed fix for 39 advisories. pip-audit finds no known vulnerabilities in the locked set (#29).
- `/log` with `config.yaml` unreadable replies `Config can't be read, so nothing was recorded. Run careerhunter doctor.` and writes nothing (#33, ADR-015).
- A key under `hard_gates` that is not a known gate is refused when the config is loaded (#31).

### Fixed
- A fetch has one 60-second total deadline across the lookup, every redirect hop and the body. A slow drip of headers or body can no longer outlast it, and the name lookup no longer has unbounded time (#30, ADR-016).
- A response body that ends before its declared Content-Length is now a failed fetch, and a body of unknown length that ends after the watchdog fired or the deadline passed is now a timeout. Before, a connection cut early could return the partial body as a success: http.client's read1 returns an empty read when a Content-Length body ends early, and TLS suppresses an unexpected end-of-file by default (#30).

## [0.3.0] - 2026-11-01

### Added
- **A Telegram bot** (`careerhunter bot run`), for one private chat only (ADR-015, ADR-016):
  - posting alerts with **Applied** and **Skipped** buttons. Applied asks for the method, then the date (today, yesterday, this week, last week, or a typed YYYY-MM-DD), and records the application in both layers through the ledger. Skipped asks for a reason and records the skip in `search.db` only;
  - `/log <link>` records a self-sourced posting, reading the company and title from the page or taking them as `/log <link> | Company | Title`;
  - `/status <ref> <status>` updates an application through the pipeline, or `/status` to choose with buttons;
  - `/activity <type> [YYYY-MM-DD] <description>` records an activity in the EI record, asking for the date with buttons when it's left out;
  - `/recent` lists the latest applications with short references and statuses.
- The chat allowlist is enforced in code. Updates from any other chat, from groups and forwarded messages get no reply, and only a hash of the chat id is logged.
- Button data is a random single-use token, checked against the chat, the message and an expiry; replies and `/status` references are matched the same way (search migration 0002).
- The bot refuses to start unless the storage guard, config (with `telegram.chat_id`), the claim checks, the Keychain token and Telegram's `getMe` all pass. The token is redacted from every error and log line.
- **Job-ad snapshots** (ADR-017): when Applied is tapped, the page or the ATS's public JSON (Workday, Greenhouse, Lever, Ashby) is saved to `snapshots/`. Otherwise the bot asks for a PDF or screenshot, which is attached to both layers.
- **Safe link fetching:** only public addresses, with the connection pinned to the checked address on every redirect hop, so DNS rebinding can't reach the local network.
- **A launchd service** (`careerhunter service install`, `uninstall` and `status`) that restarts on failure. The bot logs events only, to `logs/bot.log`, and writes a heartbeat. `doctor` checks the chat setting, the service, the heartbeat and `logs/`.
- `careerhunter bot discover` lists the chats that messaged the bot, to find `telegram.chat_id`.
- **The fit-criteria schema** (#9): optional title lanes with priorities, location rules per work model, a gap-count rubric with a tiebreaker and exempt requirements, language, credential, shift, pay and seniority gates with title exceptions, schedule limits, watchlist role filters and an agency flag, role-level exclusions, and `exclude_applied`. These are validated now and scored from Phase 3.
- `make verify-tree` runs every pre-commit hook and the pinned gitleaks over every tracked **and untracked** file. It fails on an empty file list or a missing gitleaks build instead of passing (#1).
- A pre-push guard (`scripts/pre_push_guard.py`) refuses any push that would update or delete `main`, read from the refs git actually pushes. It has a manual-only override (#4).
- `make setup` and `make hooks` set `push.default=current` and install the guard. `doctor` warns if either is missing (#4).
- `doctor` checks `exports/` and `snapshots/` and tightens anything others could read: files to 0600, folders to 0700 (#8).
- Claude Code deny rules for the guard's override variable, `--no-verify` and `core.hooksPath` (#4).

### Changed
- `search.target_titles` is optional when `search.lanes` is set; `fit_rubric` weights and thresholds are optional when `fit_rubric.gap_tiers` is set; and `schedule.watcher_interval_minutes` is optional (#9).
- `schedule.timezone` is the one place a time zone is set. It takes an IANA name or a fixed offset (`UTC`, `UTC+05:30`). If it's missing, dates use UTC and `doctor` warns. The CLI no longer uses the computer's own zone (ADR-018).

- Claude Code ask rules also cover git commands run after environment assignments, such as `TZ=UTC git commit`.
- `doctor` also checks `logs/`.
- New dependency: `truststore`, so HTTPS uses the macOS trust store.

### Fixed

## [0.2.0] - 2026-10-31

### Added
- Two data layers in the data folder (ADR-014):
  - `search.db`, the editable search and learning layer: postings, fit ratings, gaps, LLM output, scout metadata, applied and skipped decisions with skip reasons, and the full decision history;
  - `ei_record_<label>.db`, one sanitized, append-only EI record per claim. It keeps the 0.1.0 protections: no deletes, voiding, the audit log and honest dates.
- An opaque, random correlation ID links each application across the two layers. The EI record never reads or attaches `search.db`, and `export` reads only the claim's file.
- One migration track per kind of file, each with checksums, and a permanent identity recorded in every file, so one kind can't be migrated as the other.
- EI claims in `config.yaml` (`ei.active_claim` and `ei.claims`), validated for label format, dates and overlap. The active claim is set, never computed. With no active claim, nothing is written to any EI record and `search.db` keeps learning.
- **Consistent dual writes.** Every application and status update is written to both layers in a fixed order: the search database's changes are staged first but held uncommitted, the EI record then commits as the source of truth, and the search database commits last. If anything fails before the EI commit, nothing is saved anywhere. If only the final search commit fails, the EI record stands and doctor flags the gap so it can be repaired.
- `careerhunter claim seal <label>`: prints what it will do, asks for the label again, then permanently closes an earlier claim's record and makes it read-only (0400). Sealing is never automatic. `init`, `migrate` and `seed` refuse to run while an earlier claim is unsealed, and name the command to run.
- `seed` routes each record to its layer, and checks every application and activity against the active claim by date precision: an exact date must fall within the claim, a week must overlap it, and an unknown date is accepted with a warning. Re-running `seed` fills in a side that is missing.
- `seed --route-out-of-claim-to-search` records out-of-claim applications in `search.db` only, and lists each one. Activities outside the claim are always refused.
- `doctor` checks:
  - the claim config;
  - the active claim's file and its 0600 modes;
  - that earlier claims are sealed and read-only;
  - both schema versions;
  - reconciliation between the layers, in both directions;
  - leftover v0.1.0 `careerhunter.db` files.
- The status pipeline gains `hired` (offer accepted).

### Changed
- `export` now takes `--claim <label>`, and the export file names include the label.
- Statuses are renamed `assessment_submitted` and `interview_scheduled` (they were `assessment` and `interview`). EI status rows no longer carry notes; notes stay in `search.db`.
- `doctor` no longer migrates. It reports a schema that is behind and says to run `careerhunter migrate`.
- The posting `source` can also be `self_sourced`.

### Removed
- The single `careerhunter.db` and its migration. 0.2.0 never opens it for writing. No real data was ever seeded into it, so there is nothing to migrate.

## [0.1.0] - 2026-10-31

### Added
- Fail-closed storage guard. It refuses to start unless `CAREERHUNTER_DATA_DIR` is set, outside any git repository, on a mounted external volume separate from the boot disk, and that volume is encrypted, unlocked APFS. It warns loudly if FileVault is off on the boot disk.
- `careerhunter init`: creates the private data folder (mode 0700) without ever creating missing parents, copies the config templates, and creates the database.
- SQLite schema `0001_init` (WAL, busy_timeout, foreign keys) for companies, postings, applications, status history, activities, skips and an `edits` audit log. It includes:
  - CHECK-constrained enums, including ATS types (SuccessFactors, iCIMS, Taleo, Jobvite and more) and the `recruiter_inbound` method;
  - date-precision rules;
  - no-delete triggers on every table, with append-only status history and audit log.
- Posting identity by URL, else requisition ID, else company + title + location + month first seen, so re-posted roles are new postings. Re-applying to the same posting on another date is supported.
- Voiding for applications and activities: a required reason, retained in the database, excluded from exports, and frozen afterwards.
- An audit trail: triggers log every changed column of every permitted update to `edits`.
- The database, WAL and SHM files are created owner-only (0600). `doctor` checks and fixes database file permissions, and flags config files readable by others.
- A versioned migration runner with checksum verification.
- `careerhunter seed`: validated, transactional, idempotent import of past applications and activities from `seed.yaml`.
- `careerhunter export`: EI job-search record for a date range as PDF and CSV, never overwriting an earlier export, with protection against spreadsheet formula injection.
- `careerhunter secret set|verify`: macOS Keychain helper that never echoes values and refuses plaintext backends.
- `careerhunter doctor`: setup check.
- Config validation for target titles, locations, hard gates, fit rubric, schedule and watchlist. Example templates use generic values.
- Pre-commit hooks: ruff, mypy (strict), gitleaks (pinned upstream hook), and a custom check that blocks anything resolving into the data folder.
- GitHub Actions CI: lint, type check, tests with an 85% coverage floor, and a full-history gitleaks scan with a checksum-pinned binary.
- Documentation: README, SETUP, ARCHITECTURE, DECISIONS, SECURITY and CONTRIBUTING, plus issue and PR templates.
